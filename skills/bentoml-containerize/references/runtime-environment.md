# Runtime environment spec — deep reference

Two equivalent ways to define a Bento's runtime environment.

## Option A: `bentoml.images.Image` (in `service.py`)

```python
import bentoml

my_image = bentoml.images.Image(python_version="3.11").python_packages("torch", "transformers")

@bentoml.service(image=my_image)
class MyService: ...
```

### Constructor arguments

| Argument | Default | Meaning |
|---|---|---|
| `python_version` | build env's Python | e.g. `"3.11"` |
| `distro` | `"debian"` | base image family |
| `base_image` | `""` | custom Docker base image; overrides `python_version`/`distro` |
| `lock_python_packages` | `True` | lock all versions (incl. transitive deps) at build time; `False` if you pin yourself |

### Chainable methods (order-sensitive — commands run in declared order)

| Method | Notes |
|---|---|
| `.python_packages("numpy>=1.20", "git+https://github.com/user/repo.git@branch", "./wheels/pkg-0.1.0-py3-none-any.whl")` | PyPI specs, Git URLs, local wheels; `wheels/` auto-included in the Bento |
| `.requirements_file("./requirements.txt")` | existing requirements file |
| `.pyproject_toml("pyproject.toml")` | deps from a pyproject |
| `.system_packages("curl", "git")` | distro package manager installs |
| `.run('command')` | build-time shell command; runs before pip install if placed before `.python_packages(...)`, else after |
| `.run_script("scripts/setup.sh")` | run a script file (needs a shebang) |
| `.build_include("data/", "config/settings.yaml")` | extra paths copied into the build context before python packages |

Multi-service Bentos share one runtime environment; per-service images are
unsupported.

## Option B: `bentofile.yaml`

Beside `service.py`. Only `service:` is required.

```yaml
service: "service:MyService"      # <module>:<class name>
name: my-bento                    # optional; default = class name in snake_case
description: "..."
labels: {owner: my-team}
include: ["*.py", "config/"]      # relative to build ctx (default: everything)
exclude: ["tests/"]               # applied after include
python:
  packages: [torch, transformers]
  requirements_txt: "./requirements.txt"   # alternative to packages
  lock_packages: true
docker:
  distro: debian                  # debian|alpine|ubi8|amazonlinux
  python_version: "3.11"
  system_packages: [curl]
  base_image: ""                  # custom base image (advanced)
  cuda_version: "12.1"            # GPU images; incompatible with conda
# (top-level `conda:` options auto-select a miniconda image variant; no distro value)
envs:                             # env vars baked as ENV into the image
  - {name: HF_HUB_OFFLINE, value: "1"}
  - {name: HF_TOKEN}              # name only => value supplied at runtime
models: [my_model:latest]         # from the local model store
args: {}                          # template args for parametrized builds
```

Unknown top-level keys are rejected (`__forbid_extra_keys__`), so typos fail the build
clearly. Non-default path: `bentoml build -f path/to/bentofile.yaml`; other flags
`--name`, `--version` (auto-generated by default), `--label KEY=VALUE`.

## `.bentoignore`

Gitignore-style, per directory recursively: may sit at any build-context level, with
patterns relative to its own directory. `.git/`, `.venv/`, `venv/`, `__pycache__/` and
`.DS_Store` are **always excluded automatically**. Use it for large data/checkpoint
dirs. It composes with `include`/`exclude`: a file is packaged only if it matches
`include`, does not match `exclude`, and is not ignored.

## Environment variables

- **With a value:** `ARG`/`ENV` lines in the generated Dockerfile, baked into layers and
  visible to anyone with the image. Never bake secrets.
- **Without a value** (name only): documents what runtime must supply (`docker run -e`,
  Kubernetes Secret/env).
- Same list in code: `@bentoml.service(envs=[{"name": "HF_TOKEN"}])`.

## Models: baked into the image vs downloaded at runtime

Which of the three the service uses changes containerize behavior and the deployment's
needs.

### 1. Declared model references (recommended) — baked into the image

```python
import bentoml
from bentoml.models import BentoModel, HuggingFaceModel

@bentoml.service()
class MyService:
    # MUST be class variables; inside __init__ they are not registered as Bento dependencies.
    model_path = HuggingFaceModel("google-bert/bert-base-uncased")  # returns a path
    sk_ref = BentoModel("iris_sklearn:latest")                       # local model store

    def __init__(self):
        from transformers import AutoModelForSequenceClassification
        self.model = AutoModelForSequenceClassification.from_pretrained(self.model_path)
```

`bentoml containerize` resolves **all** declared models into the build context (HF
snapshots downloaded, model-store models copied), so the image carries the weights: HF
under `$BENTO_PATH/hf-models` (via the baked `BENTOML_HF_CACHE_DIR`), model-store under
`$BENTO_PATH/models`. Therefore:

- No network or token needed **at runtime**.
- Image can be multiple GB; registry and cluster must tolerate it.
- **Gated/private HF models:** `export HF_TOKEN=hf_...` in the build/containerize shell
  (huggingface_hub reads it); build time only, NOT stored in the image.
- `HuggingFaceModel(model_id, revision="main", include=[...], exclude=[...])` trims the
  download (e.g. exclude `*.bin` when safetensors exist).

### 2. Ad-hoc runtime downloads — NOT baked

A `from_pretrained("some/model")` in `__init__` with no class-level `HuggingFaceModel`
reference packages nothing: the container downloads the model **every start**. The pod
then needs outbound network and any auth token at runtime (`docker run -e HF_TOKEN=...`
locally, a Kubernetes Secret in the cluster: tell the deploy skill), and startup is slow
and unreliable. Prefer pattern 1.

### 3. Models from the local model store (`bentofile.yaml` `models:` list)

Bakes as `BentoModel` does; entries are tags in the local store (`bentoml models list`).
